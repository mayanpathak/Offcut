# v6.2implementation.md - Offcut V6.2 "AI edit plan": implementation plan

**Implements:** `buildplan.md` (BP) §8A.2, `technicalspec.md` (TS) §40.7, §40.8, §47 (the V6.2 rows), §47.2, §47.3, §47.5, §52 and the V6.2 rows of TS §41, `product.md` (PS) §8 principle 3, §9.2.1, §12.8, §12.16, all **v1.5** (the founder's decisions of 2026-11-09, `docs/v6/v6changelog.md` Entry 38, confirmed 2026-11-11, Entry 39). It is the second of the V6.x releases (BP §8A.0) and comes after V6.1 (tag `v6.1`, `main` at `b73fea5`). "V6.1 §n" is a section of `docs/v6.1/v6.1implementation.md`; "V6 CL" is `docs/v6/v6changelog.md`, **this release's changelog too** (BP §8A.0 step 1); "G n.m" is a step of `docs/v6.2/v6.2buildguide.md`. Decisions D-1 to D-432 belong to V1 to V6.1; this document continues at **D-433**. Prompts continue at **P183**.

**Reader.** Whoever writes the code. The guide gives the order of work and the commands; `coding-promptsv6.2.md` gives the prompts. This file gives the contracts and the decisions, and wins where the three disagree; where it disagrees with the specs, it says so and the copy-back (§20) fixes the spec. It was written after reading the code at `aef4a1a` (`v6.2-build`: `main`'s `b73fea5` plus the v1.5 documents and V6.1's closing entry) on 2026-11-11: every "today" below is a fact of that commit. Each decision the specs leave open is marked **(V6.2 decision)**. A change to something an earlier version froze is marked **REOPENED CONTRACT**. A number nobody has measured is marked **(assumption)**. A fact that must be read on the real thing before the code relies on it is marked **(read in P1nn)**.

**How it is built: carefully, one step at a time (the founder's decision of 2026-11-11).** "This version is very crucial because further versions depend heavily on it. I don't care if the number of prompts increases." So V6.2 is **not** an overnight run. It is run by hand, one prompt at a time, in order; a prompt starts only when the one before is committed with every box ticked; the risky parts (image drawing, the camera drift, punch words, the hook) are each split into prompts that prove one thing before the next is built on it; and the founder looks at the work at four checkpoints (§17). Speed is not a goal. 28 prompts and Setup (numbered 183 to 212, two joined, D-499), against BP §8A.0's estimate of 19.

**The one-sentence goal.** At the end of V6.2, in a build with the flags `ai_plan` and `motion` on, a person drops a clip and it opens already edited by Gemini: emphasis, a snap zoom on one word and a slow push across a sentence, an icon and an emoji under a keyword, a punch word at twice the size, a hook title over the first 2 seconds, glowing captions in the new Glow style, and a slow drift on every shot; any of them can be switched off and undone; with the API down, over quota or over the spending cap, the same clip reaches `ready` on the local rules and says so once; the Enhance panel switches Motion and Voice cleanup instantly and remembers the choice; and with both flags off, the product is exactly what it is at `b73fea5`.

**The second goal: nothing that works breaks (TS §41).** Every protected proof of TS §41.1 passes unchanged in the build production runs (flags off). With the flags on, a clip with the AI plan off and `Enhance::v5()` gives V5's frames and samples (DC-16). Every existing golden and display-list snapshot has an empty diff. Production keeps both flags off at the merge; turning them on is a separate deploy, the founder's (§14.3).

**What you can demo.** In the flags-on build with a local API holding the Gemini key: drop the reference clip. The feed says "Planning the edit". The clip opens on a hook lockup ("THE ONE THING / NOBODY TELLS YOU", one word in the accent colour) for 2 s; the shot drifts in, then out; on the claim the frame snaps in; one word fills the screen in capitals; a fire emoji pops under a keyword. The side panel lists every item with a switch; switch the punch word off, undo. The text extras panel shows a hook, a post caption and hashtags, each with a copy button. Open Enhance: switch Motion off and the drift stops at once; switch Voice cleanup off and the original sound plays, levelled; drop the next clip: both are still off. Stop the local API: the next clip reaches `ready` with the rules' visuals, and the feed says "AI plan unavailable: using the built-in rules" once.

## 7. The server

### 7.1 Types (`offcut-api-types/src/plan.rs`)

`PlanRequest { catalog: u32, duration: DurMs, words: Vec<PlanWord>, sentences: Vec<WordRange> }`, `PlanWord { text, start: TimeMs, end: TimeMs, energy_z: f32, pitch_z: f32 }`, `PlanResponse { plan: EditPlan, plans_remaining: Option<u32> }`, all `deny_unknown_fields`, generated to `web/src/gen/api.ts`.

### 7.2 Request handling, in order

1. Rate group `PlanIp` `per(10, MINUTE)` (before the body). 1b. A bearer, else 401 (D-494); then `PlanUser` `per(10, MINUTE)`. 2. Body ≤ 64 kB, JSON, parsed. 3. `catalog == CATALOG_VERSION`, else 409. 4. `PLAN_ENABLED` and the cap, else 502 `E_PLAN_UNAVAILABLE`. 5. The quota (D-461), else 429. 6. `user_message` from the request, `system_prompt()`, the schema; the provider call (25 s). 7. Parse into `EditPlan`; on failure one retry with the error appended; still failing, 502 `E_PLAN_INVALID`. 8. Set `source`; V-1; response ≤ 32 kB. 9. Count the quota and the spend; log (D-464).

## 8. The client's plan flow

### 8.1 `request-plan.ts`

Inputs: `transcript`, `prosody`, `signal`. Off (flag, switch, signed out, `navigator.onLine === false`) → rules at once, with no request. Otherwise `requestPlan(body, signal)` with a 30 s timer (**as read (P192):** 20 s, D-466 and D-498 over this line and TS §40.7's figure); map `E_PLAN_QUOTA` → `quota`, 502/504 and network failures → `unavailable` or `offline`, `E_PLAN_INVALID` → `invalid`, `E_PLAN_CATALOG` → `catalog`, timer → `timeout`. The plan is then validated in the render worker by the same `validate` the rules plan passes (`setScene` validates today: `scene_api.rs` maps `RejectReason::Catalog` to `PlanCatalog`); a model plan whose items are all dropped falls back to the rules with `invalid`. How the drops reach the use-case (`setScene`'s report gains them, or a `validatePlan` call of its own) is **(read in P193)**: an addition to the binding either way.

### 8.2 `run-pipeline.ts`

At step 11 (prosody measured), `const planned = startPlan(...)` when on; at step 12, after `rulesPlan`, `const choice = await planned`; the model plan if usable, else the rules plan; `clipStore.setPlan(plan)`; `plansRepo.put` when a request was made; the feed's line once for a fallback; `plan_result`. The stage `detect_scene` covers the wait (no new `PipelineStage` in the store; analytics' `stage_timing` gains `plan` only when a request was sent).

### 8.3 Restore and regenerate

`restore-session.ts` reads `plansRepo` first; a stored plan is validated as at the first run (DC-7 keeps catalog 1 plans readable). "Regenerate plan" (side panel, the visuals list's menu) re-requests; on success it replaces the plan and keeps overrides whose ids match; on failure a toast says why and nothing changes. **As read (P193):** `restore-session.ts` restores the account, not a clip, and no clip is restored on a reload before V7 (`start-app.ts`: `// V7: restoreClip()`). The stored plan is read where a clip's pipeline runs again (Retry, Process again): with the switch on, a plan kept for the clip is used with no request and checked again; a kept rules plan (a request that failed) gives the rules plan with no request. V7's restore reads the same record. `regenerate-plan.ts` asks with the transcript as heard, checks the answer with `validatePlan`, and hands it to `review-update.ts`' new `replacePlan` (the update queue; not a step of the history, as the edit does not change; the edit and its overrides are kept whole, and an override whose id is not in the new plan touches nothing). It returns `{ ok }` or the reason (`busy` and `failed` beside the plan's outcomes); the button and its toast are P194's, with the copy (`copy/plan.ts`).

## 10. The look

### 10.1 Camera drift (P199)

`camera::build(changes: &[OutMs], sentences: &[OutSpan], duration: OutMs) -> CameraTrack`; pure; `scale_at(t)` returns 1.0 outside segments. `video::Track::cmd(t)` computes `src` from the crop: `w' = w / s`, `h' = h / s`, centred, clamped to the source. Tests: `none()` equals today for every `t`; segments split at 4 s at the nearest sentence start; under 0.8 s still; alternation; the clamp at the frame's edge; the cap with a punch. TE-31 reads 5 s of drift rendered headless at 30 fps for visible stepping. **As read (P183):** the video pass samples a fractional crop continuously (a linear drift moved a shape 0.021-0.039 output px every frame, 0.030 expected, never zero then a jump), so the pass line is "no snapping: every frame moves in proportion to the scale's change", not a speed limit; P199 reads it on the `STANDARD` curve.

### 10.2 Captions (P201-P203)

Glow and emphasis are drawn inside `captions_draw.rs`, punch words in `captions.rs`' chunking. At `aef4a1a` each has about 390 lines of code above its test module (the limit is 700), so they have room; if either would pass 650, the new code goes in `captions_emphasis.rs` or `captions_punch.rs` instead. No existing function's output changes for a clip without the new items: the snapshots prove it.

### 10.3 Images in the scene (P204)

`events/emoji.rs` and `events/icon_pop.rs` lay out from the caption block and the word boxes (the same boxes `hit` uses); `draw` emits `Image` (and the disc's `FillRect` for an icon).

### 10.4 The hook (P205)

`lockup::lay_out(text, accent, safe_width, fonts) -> Option<Lockup>` **As read (P205):** built as `lay_out(text, accent, (width, height), fonts) -> Result<Option<Lockup>, SceneError>`: the room's height rules out a split too tall, and a font error is the scene's error, not a hook that does not fit: tries 2 then 3 lines, every split of the words, sizes from 140 lp down to 48 lp (assumption) in steps of 4; scores each by the worst line's distance from the safe width; ties go to fewer lines. Pure, deterministic, tested on short, long, one-word and impossible hooks.

### 10.5 The cost

P206 measures `frame_at` with every kind on the reference clip in a release build: the scene's part of the 150 ms edit budget and the per-frame time at export (V5's readings are the bar; a cost above 1.5× today's per frame is a stop-and-ask). **As read (P206):** 0.78-1.23× today's per frame in the four styles, every frame in microseconds (experiments.md, §10.5).
